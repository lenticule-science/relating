# Decision: the carrier `$id` scheme

## The question

Phase 1 of the [refactor roadmap](2026-06-21-refactor-roadmap.md) needs the carrier `$id` scheme fixed before any `object.schema.json` is authored, because `$id` becomes (a) carrier identity, (b) the cross-package `$ref` target, and (c) the key of the schema registry that Phase 1 §5 and Phase 2 §2 resolve against.
The roadmap posed it as a binary: path-form (`relating/articulating/utterance`) vs URL (`https://561.group/...
`).
The initial lean was toward URL on "more robust over time" grounds.
This note is the deep answer that question was given.

## The answer

**Store `$id` as the package-rooted descent path, bare:** `relating/articulating/utterance`. **Never bake a domain authority into it.** When a dereferenceable absolute URL is genuinely needed — standard JSON-Schema tooling, linked-data publication — produce it by prepending a base **at the boundary**, exactly as the corpus already projects IRIs from slugs.
Robustness over time lives in the serving/redirect layer (cool URIs), not in the stored identifier.

This is a synthesis, not a coin-flip: it gives the user's robustness goal its real home (the edge) while keeping identity location-independent, which is what every other identity surface in this codebase already does.

## Why — the evidence, in order of force

### 1. The corpus naming law forbids provenance/authority segments in identity

`content/CLAUDE.md` states the law in primary-source terms:

- *"The depth is the memory.
  The long rhyming tree **is** the addressing system — a typed-term language of pointers."* Identity **is** the descent path.
- *"Read a path left to right and it is a proof — each segment is generated by the one before it."* `relating/articulating/utterance` reads as a proof (relating generates articulating generates utterance).
  Prepending `https://561.group` inserts a segment generated by **nothing in the descent** — a hosting authority — breaking the left-to-right proof reading.
- *"**No provenance segments, ever** — no `from-<source>/`, no repo names, no hashes.
  A provenance segment is a lie about what the file is."* A DNS authority (`561.group`, `research-notes.
  561.group`) is precisely a provenance/location segment: it says *who serves a copy*, not *what the carrier is*.

A carrier's identity is its generated position in the relating descent, not the name of a server that happens to host a representation of it.

### 2. The live code already chose location-independent, scheme-qualified identity

For addressable artifacts, `acting/induce.mts` and `acting/resource.mts` already mint identity as `relating://<package>/schema/<verb>/<side>` and `relating://<package>/discovery` — absolute (it has a scheme) yet **deployment-free** (no `https`, no domain).
When the codebase needed artifact identity it did *not* reach for `https://561.group`; it reached for a locationless scheme.
The `$id` decision should match that instinct, and the bare descent path is its purest form.

### 3. Our own web theory stores the relative term and projects the URL at the edge

`lib/computing-with-the-semantic-web` is the strongest possible counter-source — it literally implements `cool-uris` ("Cool URIs don't change") and `linked-data`.
It *agrees* with this decision:

- `linked-data` vocabulary: *"A thing the site holds settled claims about; **its slug is its IRI**."* Stored identity is the slug.
  The absolute IRI is computed: `subjectIri(base, subject) = ensureSlash(base) + encodeURI(subject)` — `base` is a boundary parameter, never part of the stored term.
- `cool-uris`: representations are stored as **relative paths**; the absolute URL is computed only against the live request, `new URL(path, requestUrl).href`.
  Durability ("cool URIs don't change") is delivered by the **303 + `Link` + `Vary`** negotiation layer — a serving concern — not by embedding a domain in every identifier.

So "robust, dereferenceable, stable URLs" is a solved problem in this repo, solved at the edge.
Baking `https://561.group/...
` into `$id` would duplicate that concern in the wrong layer and re-couple identity to one deployment.

### 4. URL-form `$id` has already failed in this exact repository

The schema tree under `lib/561-group/working/.../composting/...
` used URL-form `$id`.
The result, observable today:

- **Self-concatenated identifiers** — e.g. `…/dispatching/library/dispatching-an-inquiry/https://research-notes.
  561.group/…/dispatching-an-inquiry.schema.json` — absolute URLs path-joined into themselves, because something resolved a stored absolute URL as if it were relative.
- **Authority drift** — `research-notes.
  561.group` and `561.group` both appear as `$id`/`$ref` authorities in the same tree.
- **Mixed `$ref` styles** — some full-URL, some relative `../x.schema.json`.

This is not hypothetical fragility; it is the demonstrated failure mode of storing long absolute URLs as identity.
The clean schema in the new line (`relating/articulating/utterance`) is bare path-form.
The empirical record in our own tree contradicts the "URL is more robust" prior.

### 5. The JSON Schema spec does not force URL-form, and our resolver doesn't need it

JSON Schema 2020-12 requires `$id` to be a **URI-reference**; a relative reference is permitted.
It *prefers* an absolute-URI only because that gives a stable base for resolving relative `$ref`s in standard, document-fetching validators.
This ecosystem does not resolve that way: it carries its **own** schema machinery (`codecs/schema.mts` matches `$id` by exact string; `projectSchemaAssertions` checks claimed `$id` against an expected string), and the roadmap's registry (Phase 1 §5) / producer→consumer matching (Phase 2 §2) are **exact-string** operations.
Path-form strings are perfectly good registry keys and `$ref` targets; nothing in the planned architecture needs an http authority.
If a standard validator is ever adopted, the cool-uri base-prepend (point 3) absolutizes ids at that one boundary — the same move the repo already makes for serving.

## Consequences / how to apply

- Author every `object.schema.json` with `$id` = its package-rooted descent path, bare: `relating/articulating/utterance`, `gaming/<…>`, `computing/<…>`.
  The path segments are the morphism/object descent, matching `content/`'s tree.
- An action references carriers by that exact string in `inputSchema`/`outputSchema` `$ref` (roadmap §Phase 1.4); the registry is keyed by that exact string.
- Intra-document references stay JSON-pointer (`#/$defs/Token`), as today.
- If/when schemas are published dereferenceably, add a serve-time base-prepend (reuse the cool-uris / `subjectIri(base, …)` pattern); do **not** rewrite stored `$id`s to absolute URLs.
- Do not import the corrupted `lib/561-group/working/...
  ` URL-form convention; per `CLAUDE.md` Absence, its breakage is evidence the old way was wrong.
